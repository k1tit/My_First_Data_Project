# Домашнее задание №3. Бенчмаркинг продукта

## 0) Контекст проекта

**Продукт:** AI-система оценки финансового риска и поведенческого профиля клиента для кредитного контура банка/финтеха (MVP — скоринг дефолта; расширение — флаги подозрительных паттернов дохода).  
**Цель бенчмаркинга:** зафиксировать стандарты продукта через **конкретные** конкурирующие решения на российском рынке и сопоставить с ними измеримые (или обоснованные сценарно) метрики.

---

## 1) Целевая аудитория (ЦА) и её проблема

### 1.1 Кто ЦА

**Покупатель / заказчик:** средний или крупный банк или лицензированный финтех, выдающий потребительские кредиты физлицам в РФ (кредитный департамент + риск-менеджмент).

**Пользователи продукта:**

| Роль | Задача |
|------|--------|
| **Риск-аналитик** | Настройка порогов, разбор спорных заявок, мониторинг качества модели |
| **Кредитный менеджер** | Решение по заявке при ручном эскалационном потоке |
| **Система принятия решений (API)** | Автоматический approve / review / decline по скору |

**Сегмент заёмщика (конечный клиент банка):** физлица с заявкой на потребительский кредит, в том числе с историей платежей в банке, но без полной «выписки» по всем источникам дохода.

### 1.2 Проблема ЦА (Jobs / pains)

1. **Высокие потери от дефолта** — неточный скоринг → в одобренный поток попадают рискованные клиенты (цель: снизить bad rate при том же уровне одобрений).
2. **Разрозненные контуры** — кредитный скоринг, антифрод и AML живут в разных системах → аналитик не видит **единый** профиль риска по клиенту.
3. **Слабый учёт поведения** — решение в основном по анкете и БКИ; **платёжное поведение** и признаки «доход в анкете ≠ поведение» почти не влияют на скоринг (этап 2 — флаги подозрения, не налоговая квалификация).
4. **Перегруз ручной проверкой** — много заявок уходит на аналитика; высокая доля **ложных алертов** в мониторинге (фрод/AML) отвлекает от реального риска.
5. **Медленные и непрозрачные решения** — долгий time-to-decision и «чёрный ящик» без reason codes → падает конверсия и растёт операционная стоимость.

**Связь с бенчмаркингом:** сравниваем не «классы систем», а **конкретные продукты**, которыми ЦА уже пользуется или которые задают ожидания рынка по скорости, автоматизации и качеству отсечения риска.

## 3) Обоснование метрик бенчмарка

Метрики выбраны из **проблем ЦА** (п. 1.2):

| Метрика | Тип | Зачем ЦА | Как измеряется у конкурентов |
|---------|-----|----------|------------------------------|
| **AUC-ROC / Gini скоринга дефолта** | Техническая | Качество ранжирования риска | Почти **не публикуется** → сценарий + наш целевой порог с пилота |
| **Bad rate в одобренном потоке** (или NPL розницы) | Продуктовая | Прямой эффект на P&L | Макро: отчётность / обзоры ЦБ по банку; не разрез по одной модели |
| **Доля автоматических решений** (без ручного аналитика) | Продуктовая | Снижение cost-to-serve | Маркетинг/описание продукта («решение за N минут») + отраслевые допущения |
| **Время скоринга заявки (p95)** | Операционная | Конверсия воронки, SLA API | Публичные обещания канала + SLA вендоров |
| **Доля ложных алертов (FP) в мониторинге** | Операционная | Боль №4 — перегруз аналитиков | Кейсы вендоров/банков; сценарий для rule-based |
| **Время разбора одного кейса аналитиком** | UX / операционная | Стоимость ручного контура | Пользовательский сценарий (норматив) |
| **Доступность сервиса (SLA)** | Операционная | Непрерывность кредитного конвейера | Договорные SLA вендоров / внутренние SLO |

**Целевые значения нашего продукта** (пилот/MVP) согласованы с `business_understanding.md`: AUC с нижней границей доверительного интервала ≥ 0,75; прирост AUC к baseline ≥ 0,02; продуктовые прокси — снижение bad rate в одобренных, снижение FP алертов на этапе 2.

### 4.2 Как получены значения (прозрачность)

| Конкурент | Что измерено публично | Что через сценарий |
|-----------|----------------------|-------------------|
| **Т-Банк** | Скорость онлайн-решения, высокая доля цифрового канала | % авто-решений, AUC |
| **Сбер / ВТБ** | Масштаб розницы, NPL в отчётности | % авто-решений, время ручного кейса, AUC |
| **Сбер антифрод** | Факт внедрения real-time мониторинга; кейсы снижения FP при ML | Точный FP rate по продукту |
| **Диасофт AML** | SLA и режимы batch/online в описании продукта | FP и время офицера без доступа к банковским KPI |

**Пользовательские сценарии (пример для обоснования FP):**  
*Риск-аналитик mid-size банка получает **100 алертов/день** по rule-based мониторингу; **70** закрываются как ложные после проверки → FP **70%**. Цель нашего гибридного контура — снизить до **~55%** (−15 п.п.) за счёт контекста клиента и кредитного скора.*

**Пользовательский сценарий (время кейса):**  
*Кредитный менеджер без reason codes тратит **30–45 мин** на сбор данных из разных систем; единая карточка риска сокращает до **10–15 мин**.*

## 6) Анализ и сравнение с будущим продуктом

### 6.1 Обязательные функции (чтобы не проиграть конкурентам из таблицы)

- Скоринговый API / batch с **p95 ≤ 1 с** на заявку.
- Интеграция анкеты, бюро и **поведенческих агрегатов** (платежи, балансы).
- Пороги approve / review / decline и **reason codes**.
- Мониторинг AUC, bad rate, стабильности по сегментам.
- (Этап 2) Очередь подозрительных паттернов дохода с приоритизацией.

### 6.2 Отличия и устранение недостатков конкурентов

| Недостаток конкурентов | Наш ответ |
|------------------------|-----------|
| Раздельные скоринг / фрод / AML | Единая карточка клиента; MVP — кредитный скор, этап 2 — risk flags |
| Нет поведения в кредитном скоре | Агрегаты `installments_payments`, bureau |
| Высокий FP в мониторинге | Контекст кредитного скора + приоритизация кейсов |
| «Чёрный ящик» | SHAP / reason codes |

### 6.3 Монетизация и UX

- **Монетизация B2B:** лицензия + внедрение + подписка; переменная часть за объём заявок/кейсов.
- **UX риск-аналитика:** одна очередь, drill-down по признакам, оценка ожидаемых потерь по кейсу.
