# 1. Бизнес-анализ (Business Understanding)

**Название проекта:** AI-система оценки финансового риска и поведенческого профиля клиента.

## 1.1 Организационная структура

Проект реализуется в рамках финансовой организации (банк или финтех-компания), предоставляющей кредитные продукты физическим лицам.

### Участники проекта со стороны заказчика

- Бизнес-заказчик — кредитный департамент / риск-менеджмент (определяет бизнес-правила и KPI).
- Владелец продукта (Product Owner) — отвечает за внедрение модели в бизнес-процессы.
- Риск-аналитики — эксперты в области кредитного скоринга и оценки дефолтных рисков.
- Data Engineering команда — обеспечивает доступ к данным и их подготовку.
- IT / ML инженеры — реализация модели и интеграция в систему принятия решений.

### Основные пользователи системы

- Кредитные менеджеры (при ручном рассмотрении заявок).
- Автоматизированная система скоринга (API для принятия решений о выдаче кредита).
- Риск-аналитики (для мониторинга качества портфеля).

### Бизнес-цель проекта

**Основная цель:**

Повышение качества оценки кредитного риска клиентов за счет построения AI-системы, учитывающей поведенческие и транзакционные финансовые данные.

**Дополнительные бизнес-цели:**

- Выявление "несанкционированных" и нетипичных поступлений на счета клиентов (и выявление недекларированных доходов).
- Снижение уровня дефолтов по кредитам.
- Повышение точности кредитного скоринга.
- Снижение финансовых потерь организации.
- Улучшение сегментации клиентов по уровню риска.

### Существующие решения

В настоящее время в организациях подобного типа используются следующие подходы:

- **Rule-based системы**
  - Принятие решений на основе фиксированных правил (доход, возраст, кредитная история).
  - Ограниченная гибкость и слабая адаптация к новым паттернам поведения.
- **Классические скоринговые модели**
  - Логистическая регрессия и scorecard-модели.
  - Используются как baseline, но имеют ограниченную выразительность.
- **ML-модели (частично внедренные)**
  - Градиентный бустинг (XGBoost, LightGBM).
  - Используются для кредитного скоринга, но без глубокого анализа транзакционного поведения.

**Ограничения существующих решений:**

- Слабый учет поведенческих паттернов клиента во времени (динамика платежей, использование кредитных линий).
- Отсутствие глубокого анализа транзакционных данных для выявления "несанкционированных" поступлений и скрытых доходов.
- Ограниченная способность оценивать надежность клиентов с отсутствующей или короткой кредитной историей.
- Недостаточная интерпретируемость сложных моделей.

- GPU не является критически необходимым (если не используются нейросети).


### Риски проекта и их минимизация

#### 1) Риск несоблюдения сроков

**Причины:**

- Задержка доступа к данным.
- Сложность интеграции источников данных.

**Митигация:**

- Использование комплексного открытого датасета (Kaggle Home Credit Default Risk) со связанными таблицами.
- Поэтапная реализация (MVP -> расширение).

#### 2) Риск низкого качества данных

**Причины:**

- Пропуски, шум, несогласованность источников.
- Неполные транзакционные данные.

**Митигация:**

- Этап Data Cleaning и Feature Engineering.
- Использование устойчивых агрегированных признаков.

#### 3) Риск слабой предсказательной способности модели

**Причины:**

- Недостаточная информативность признаков.
- Слабая связь между поведением и дефолтом.

**Митигация:**

- Расширение признакового пространства (поведенческие + транзакционные фичи).
- Использование ансамблевых моделей.

#### 4) Риск отсутствия интерпретируемости

**Причины:**

- Сложность моделей (градиентный бустинг, ансамбли).

**Митигация:**

- Использование SHAP / feature importance.
- Комбинирование с интерпретируемыми моделями.

#### 5) Риск смещения выборки из-за reject inference

**Причины:**

- Таргет наблюдаем только для заявок, по которым кредит был выдан.
- Для отказанных заявок фактический исход (дефолт/не дефолт) недоступен.

**Митигация:**

- В MVP явно фиксируется область применимости модели: похожий на обучающий поток заявок.
- Контроль стабильности метрик по сегментам (в т.ч. "тонкие" сегменты с короткой историей).
- Калибровка вероятностей и анализ смещения ошибок.
- На следующих итерациях при расширении данных: применение reject inference подходов (champion/challenger, parceling/augmentation).

## 1.3 Data Mining Goals

### Приоритет реализации (MVP)

- **Приоритет MVP:** кредитный скоринг (бинарная классификация дефолта).
- **Вне MVP (следующий этап):** модуль выявления "несанкционированных" поступлений и аномалий транзакционного поведения.
- На этапе MVP критерии успеха и основные ресурсы фокусируются на задаче скоринга.

### Логика построения таргета (Target Definition)

В качестве целевой переменной используется `TARGET` из `application_train.csv` (Kaggle Home Credit Default Risk):

- `TARGET = 1` — клиент с дефолтом (риск реализовался).
- `TARGET = 0` — клиент без дефолта.

Для MVP таргет не переопределяется, чтобы сохранить сопоставимость с benchmark-решениями на этом датасете и обеспечить прозрачную проверку гипотезы.

Бизнес-интерпретация таргета: модель оценивает вероятность дефолта по заявке, а score используется для ранжирования клиентов по риску при принятии решения (одобрение/отказ/ручная проверка).

### Тип задачи

В рамках MVP проект решает одну задачу:

- **Бинарная классификация** — прогноз вероятности дефолта клиента (0/1).

Задача выявления транзакционных аномалий (Anomaly Detection) выносится на следующий этап после подтверждения ценности MVP-скоринга.

### Метрики качества

**Для задачи кредитного скоринга:**

- AUC-ROC (основная метрика).
- Precision / Recall (в зависимости от бизнес-рисков).
- F1-score (баланс классов).

**Для задачи выявления аномалий:**

- Precision@K (качество топ-N подозрительных случаев).
- Recall (способность находить аномалии).

### Критерий успешности

Точечное значение метрики (например, AUC = 0,78 на одном фолде) **недостаточно** для вывода «гипотеза подтверждена». Фиксируем **оценку + доверительный интервал (ДИ)** на том же сплите валидации, что и у baseline.

- **AUC основной модели:** целевой уровень — нижняя граница 95% ДИ **не ниже 0,75** (приемлемо) или **0,80** (сильный результат).
- **Прирост к baseline (ΔAUC):** гипотеза о ценности поведенческих признаков считается подтверждённой, если 95% ДИ для **ΔAUC = AUC(модель) − AUC(baseline)** **не включает 0** и нижняя граница **≥ 0,02** (порог уточняется после первого прогона).
- **Способ оценки ДИ (MVP):** stratified K-Fold (k = 5): метрика на каждом фолде → среднее и 95% ДИ по фолдам; для сравнения двух моделей — **bootstrap по out-of-fold предсказаниям** или парный bootstrap разности AUC на одной и той же выборке.
- Baseline для сравнения: логистическая регрессия на анкете + агрегаты бюро **без** поведенческих фич (число baseline фиксируется после первого прогона).

**Дополнительно:**

- Снижение доли ложноположительных решений (также с ДИ при симуляции порога).
- Устойчивость модели на разных сегментах клиентов (AUC и ДИ внутри подгрупп).

# 2. Прототип продукта (домашнее задание №2)

Ниже — конкретизация прототипа под проект **«AI-система оценки финансового риска и поведенческого профиля»** и датасет **Kaggle Home Credit Default Risk**. Термин «транзакции» здесь означает доступные в данных **платежи по прошлым кредитам и динамику балансов по продуктам** (`installments_payments`, `credit_card_balance`, `POS_CASH_balance`), а не полную банковскую выписку по счёту.

## 2.1 Ключевая гипотеза (один сценарий, один сегмент, одна монетизация)

**Продукт A:** скоринговая модель дефолта, которая в дополнение к анкете и данным бюро использует **поведенческие агрегаты** по истории платежей и балансов, включая признаки **нерегулярных и относительно крупных платежей** (прокси «разовых вливаний», не похожих на устойчивый «зарплатный» ритм обслуживания долга).

**Сегмент B:** клиенты из `application_train`, у которых для текущей заявки есть **непустая история** в `installments_payments` и/или в `credit_card_balance` / `POS_CASH_balance` (то есть сегмент «с поведенческим следом»; объём сегмента фиксируется в ноутбуке прототипа по факту join).

**Сценарий C:** на момент рассмотрения заявки риск-контур должен **ранжировать клиентов по вероятности дефолта**, чтобы принимать решение об одобрении/отказе или о приоритете ручной проверки. В прототипе это воспроизводится как **офлайн-скоринг** на исторической выборке с известным исходе (`TARGET`).

**Монетизация (одна, банковская):** за счёт более точного отсечения/ранжирования риска снижается **ожидаемый кредитный убыток** (меньше дефолтов среди одобренных при контролируемом уровне отказов). В учебном прототипе монетизация не считается в деньгах, а **проверяется прокси-метриками** на исторических данных (см. п. 2.2): улучшение отсечения плохих кейсов при фиксированной доле одобрений или снижение доли дефолтов в топ-K самых рискованных.

**Гипотеза в требуемом формате:**

Если мы предлагаем **продукт A** для **сегмента B** в **сценарии C**, то **95% ДИ для AUC-ROC** на стратифицированной кросс-валидации (тот же сплит, что у baseline) будет с **нижней границей не ниже 0,75**, а **95% ДИ для прироста ΔAUC относительно baseline** — **строго выше 0** и с нижней границей **не ниже +0,02** в течение **2 недель итераций прототипа**, потому что **паттерны обслуживания долга и нерегулярные крупные платежи** несут информацию о платёжеспособности, которой недостаточно в анкете и статике бюро.

**Как интерпретируем результат:** если ДИ для ΔAUC включает 0 — **гипотеза не подтверждена** (эффект статистически не отделим от шума выборки на выбранном сплите). Если нижняя граница ΔAUC > 0, но < 0,02 — эффект есть, но **ниже заранее зафиксированного порога** (оформляем как слабое подтверждение).

*(Пороги 0,75 / +0,02 и метод ДИ согласуются с наставником до финального замера.)*

## 2.2 Ключевые метрики (продуктовые и технические)

Измерения в прототипе **офлайн** на Kaggle; «частота» — на время учебного спринта.

| Метрика | Тип | Baseline | Цель / порог | Как меряем | Доверительный интервал (95%) | Частота |
|--------|-----|----------|--------------|------------|------------------------------|---------|
| AUC-ROC | техническая | LR: анкета + бюро, без поведенческих фич (число после 1-го прогона) | нижняя граница ДИ ≥ 0,75; ΔAUC: нижняя граница ДИ ≥ 0,02 | Stratified K-Fold (k=5), один pipeline | по фолдам: mean ± t-based CI; финально — bootstrap по OOF-скорам | после значимых изменений; финал спринта |
| ΔAUC (модель − baseline) | техническая (проверка гипотезы) | 0 | ДИ **не пересекает 0**; нижняя граница ≥ 0,02 | та же CV, сравнение на одинаковых фолдах | bootstrap разности AUC на OOF (≥1000 итераций) или CI по фолдам | вместе с AUC |
| PR-AUC | техническая | тот же baseline | Δ(PR-AUC): нижняя граница ДИ > 0 | `average_precision_score`, те же сплиты | как для AUC | как для AUC |
| Доля дефолтов в топ-10% по скору | продуктовая прокси | baseline | ниже baseline; ДИ разности не включает 0 в «пользу» модели | сортировка по `predict_proba`, топ-10% | bootstrap по фолдам | финал / смена модели |
| Bad rate при фиксированном пороге отсечения | продуктовая прокси | правило: отказ верхним 20% по скору baseline | не хуже baseline по bad rate в одобренных (с ДИ) | симуляция на OOF-предсказаниях | bootstrap доли дефолтов | финал спринта |
| AUC по подгруппам | тех. + продукт. | AUC общей модели | нет падения > X п.п. относительно общего (X фиксируем, напр. 0,03) | подгруппы: мало записей в `bureau`, короткая история платежей | CI внутри подгруппы (если n достаточен) | перед сдачей |

**Способ измерения (общий):** один pipeline препроцессинга на train фолда; без утечки `TARGET`. **Вывод по гипотезе** формулируем только по **ДИ ключевых метрик** (в первую очередь ΔAUC), а не по одной точечной цифре.

**Пример формулировки в отчёте:** «AUC = 0,78 [0,76; 0,80], baseline = 0,74 [0,72; 0,76], ΔAUC = 0,04 [0,01; 0,07] → гипотеза подтверждена на уровне 95% ДИ».

## 2.3 Объём прототипа: что входит и что намеренно не делаем

**Входит в прототип (MVP продукта на данных):**

- Загрузка и описание схемы Home Credit, базовый **Data Understanding**.
- **Baseline:** логистическая регрессия (или линейная модель) на признаках без «глубокого» поведения.
- **Основная модель:** градиентный бустинг (XGBoost / LightGBM / CatBoost) с тем же валидатором.
- Feature engineering: агрегаты по `bureau`, `previous_application`, **платежи и балансы**; отдельный блок фич под **нерегулярность и крупные платежи** из `installments_payments` (и при необходимости — динамика `credit_card_balance`).
- Сравнение метрик, короткий **error analysis** (где модель ошибается).
- Интерпретация: **SHAP** или важность признаков для объяснения вклада «поведения».

**Намеренно не делаем в этом прототипе (и почему):**

- **Продакшен-API и интеграция в банк** — вне горизонта учебного прототипа; цель — доказать ценность сигнала на данных.
- **Реальные банковские транзакции с категорией «зарплата»** — их нет в Kaggle; гипотеза про «крупные поступления вне ЗП» реализуется **прокси** через платежи по кредитам и балансы.
- **Полноценный AML / санкционный мониторинг** — другой регуляторный контур и другие данные.
- **Нейросетевой sequence-моделинг по времени** — дороже в отладке; бустинг на агрегатах достаточен для проверки гипотезы прототипа.
- **Онлайн A/B тест** — нет живого трафика; ограничиваемся офлайн-прокси метриками.

- **Честное описание ограничений данных** (что именно называем «транзакционностью» в Home Credit).

## 2.5 Главный риск, который проверяем прототипом, и конечный вид прототипа

**Главный риск:** поведенческие признаки (включая прокси «крупных нерегулярных платежей») **не дают устойчивого прироста** к качеству модели относительно сильного baseline на анкете + бюро **на выбранном сегменте**, либо прирост есть в среднем, но **ломается на важных подгруппах** (например, мало истории платежей).

**Конечный формат сдачи прототипа:**

- Репозиторий (или архив) с **ноутбуком(ами)**: данные → baseline → фичи → обучение → **таблица метрик с 95% ДИ** (AUC, ΔAUC) → вывод «гипотеза подтверждена / нет».
- **Краткий текстовый вывод (1–2 страницы)** или раздел в том же репозитории: гипотеза, сегмент, что сделали, цифры, ограничения Home Credit.
- По возможности: `requirements.txt` и **фиксированный random seed** для воспроизводимости.

## 2.6 Критерии остановки теста прототипа

Остановка не «когда устали», а по заранее заданным правилам:

1. **Гипотеза подтверждена:** 95% ДИ для AUC — нижняя граница ≥ 0,75 **и** 95% ДИ для ΔAUC не включает 0, нижняя граница ≥ 0,02.
2. **Гипотеза не подтверждена:** 95% ДИ для ΔAUC **включает 0** (или верхняя граница ΔAUC ≤ 0) — фиксируем как результат эксперимента, не «провал», а отрицательный вывод с цифрами.
3. **Исчерпан лимит спринта** — публикуем лучший замер **с ДИ** и интерпретацию (подтверждена / не подтверждена / ниже порога).
4. **Нет прогресса:** после 2–3 итераций верхняя граница 95% ДИ для ΔAUC ≤ 0 — останавливаемся, документируем причины (данные, сегмент, слабые фичи).
5. **Качество данных/сегмента:** если после честного join сегмент B становится слишком маленьким или сильно смещённым — **останавливаемся**, пересматриваем определение сегмента (шире/уже) **одним** пересмотром и документируем.
